## Deferred / documented limitations

| Item | Reason | Where documented |
| --- | --- | --- |
| Web Push (background browser notifications while the tab/browser is closed) | Requires a service-worker `push` handler, a server holding VAPID-signed push subscriptions, and a dispatch scheduler — none of which exist yet; the brief explicitly allows deferring this with honest documentation | `reminders-and-notifications.md` §Web Push is explicitly deferred |
| `search:reindex`/`reminders:dispatch`/`saved-searches:check` standalone CLI scripts | Not added — there is no server-side batch job for any of these in this checkpoint's design (reminders/alerts regenerate deterministically on app-open, not via cron), so a CLI wrapper would duplicate the staff UI's "Refresh search statistics" action without serving a real operational need | This file; `checkpoint-4-architecture.md` §Staff discovery-quality support page |
| Staff discovery-quality queues scoped to published opportunities only | Matches exactly what students can discover today; broadening to draft/in-review opportunities would require a second, unpublished-data repository query outside this checkpoint's scope | `checkpoint-4-architecture.md` §Staff discovery-quality support page |
| Comparison selection stays client-side (localStorage), never synced to an account | Deliberate: it's non-durable browsing state, not a record worth its own RLS-governed table | `checkpoint-4-architecture.md` §Comparison |
| Notifications excluded from the guest→cloud **migration** path (still included in backup/export/import) | Ephemeral, auto-regenerating data — resurrecting old notification rows during a one-time migration isn't meaningful the way saved searches/reminders/eligibility answers are | `checkpoint-4-architecture.md` §Guest ↔ cloud parity for every new data type |
