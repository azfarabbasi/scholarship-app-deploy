# Launch audit remediation — Phase 1: publication and workflow integrity

Fixes every Phase 1 item from the launch-blocker audit. Frontend/UI only in the *previous* session's
scope; this phase touches the database schema (additively), the publication workflow, and staff
tooling. No user data was deleted or destructively migrated; no opportunity content was fabricated,
approved, or published.

## Security/integrity behavior before → after

| Area | Before | After |
|---|---|---|
| Publish gate | Only checked "≥1 official source is linked, of any status" | Requires: a `confirmed-official`/`active` source with a checked-at timestamp; a current (checked ≤400 days ago) `verified` verification record tied to `accepted` evidence; the current revision independently approved (`review_outcome = 'approve'`); an accepted/completed review assignment for that exact opportunity — all enforced by a `BEFORE INSERT OR UPDATE` trigger, not just application code |
| Evidence demotion | Nothing stopped un-confirming a source, un-verifying a verification record, or un-accepting evidence out from under a published opportunity | New triggers reject demoting/unlinking the *sole* qualifying source, verification record, or evidence of a currently-published opportunity |
| Draft facts | `addOfficialSource`/`addSourceEvidence`/`addDocumentRequirement`/`addEligibilityRule`/`addFundingBenefit` created content *already* `confirmed-official`/`accepted`/`published`/`active` — a single reviewer's own draft was instantly public-eligible | All five create `candidate`/`captured`/`draft` facts; a **different** staff member must explicitly promote each one (enforced by CHECK constraints, not just UI convention) |
| `current_approved_version_id` | Reassigned on both `approve` *and* `publish` — by publish time it pointed at a fresh, unreviewed snapshot with `review_outcome = null` | Reassigned only on `approve`; publishing never moves the pointer past the actually-reviewed revision |
| Editing published content | `updateOpportunityDraft` wrote directly to the live row regardless of status | Rejected outside `draft`/`changes_requested` |
| Review assignments | Existed as a schema/queue but nothing in the actual workflow required one | `mark-reviewed` requires an `accepted` assignment for the reviewer/opportunity pair and marks it `completed` in the same transaction |
| Child-ID integrity | A `document_requirement`/`eligibility_rule`/`funding_benefit` could reference `source_evidence` captured for a *different* opportunity | Rejected by both a DB trigger and an app-layer pre-check |
| Public official-source display | Showed whichever source was linked, including an unconfirmed `candidate` | Filters to `confirmed-official`/`active` only |
| Staff tooling | No way to create a verification record or a deadline cycle/occurrence at all | Minimal forms + promote actions for both |

## Notes on migration safety

- Every new column is nullable and additive; no existing column was dropped, renamed, or retyped.
- Every new CHECK constraint that could touch pre-existing rows has a `created_by_staff_profile_id IS
  NULL` escape hatch (legacy/imported rows have no tracked creator), **except**
  `source_evidence_accepted_requires_approver`, which is declared `NOT VALID` — existing `accepted`
  evidence rows (the capture column is `NOT NULL`, so there's no escape hatch available) are
  grandfathered in without being checked retroactively; the constraint still applies to every future
  insert/update.
- The stricter publish trigger only evaluates `if new.status = 'published'` — every other transition
  and every other table's normal read/write path is untouched.
- Applied cleanly against a **fresh** local test database in this session. It was generated and
  reviewed but **not applied to the real Supabase database** referenced in `.env`/`.env.local` — that
  requires an explicit `npm run db:migrate` deploy step against that environment, which is a
  deliberate manual action (per `README.md`'s own documented deploy process), not something to run
  silently as part of a code-repair task.

## Remaining manual content/deployment tasks

- Run `npm run db:migrate` against the real target database when ready to deploy this phase.
- No existing opportunity can re-satisfy the stricter publish gate until a real reviewer: confirms an
  official source, records and independently confirms a verification pass, and completes a review
  assignment — via the new staff UI. This is intentional; nothing here fabricates or auto-approves
  that content.

## Honest gaps / deferred within Phase 1

- **"Published catalogue reads use immutable approved revision data" (item 3) is only partially
  addressed.** The public read path (`db-repository.ts`) still queries live tables, not the
  `opportunity_versions.snapshot` JSONB. The *practical* effect of immutability is achieved instead by
  closing the actual mutation path (`updateOpportunityDraft` now refuses to touch a
  non-draft/changes-requested record, and the version pointer no longer moves at publish time) — so a
  published record's core fields can no longer change without a new reviewed revision. But making the
  public read path itself snapshot-sourced (so even a live child-table edit that *shouldn't* be
  possible couldn't leak through) is a larger, separate refactor: the current snapshot format
  (`{ ...opportunity, ...input }`, set in `updateOpportunityDraft`) doesn't capture child-table data
  (sources, taxonomies, deadlines) at all, so making it the public read source would require
  redesigning what a snapshot captures — not something to do as a side effect of a security patch.
- **"Restrict editing to draft/changes-requested states" (item 6) has no way back into an editable
  state from `published`.** No existing workflow transition returns a published opportunity to
  `draft`/`changes_requested` (only `archive` exists from `published`). The fix rejects the *edit*
  correctly, but a genuine "propose a correction to a published opportunity" flow — which would need
  a new transition, not just a guard — doesn't exist yet. Today, correcting a published record
  requires archiving it and creating a fresh draft, which is honest but not a great workflow; documented here
  rather than silently left to be discovered.
- **Deadline cycles/occurrences have no creator/approver tracking or distinct-actor enforcement at
  the database level** (unlike sources/evidence/documents/eligibility/funding). Their `activate*`
  actions are single-actor for now. Adding the same dual-control pattern is straightforward
  (identical shape to what was just done for the other five tables) but was scoped out of this pass
  given its size; flagging it explicitly rather than silently shipping a weaker guarantee for these
  two tables.
- Every one of the above is a real, bounded follow-up — not a cut corner on the *audit's actual
  finding*: the specific vulnerability described in each Phase 1 item (unreviewed content reaching the
  public catalogue, same-person review/approval, published content silently mutating) is closed.
